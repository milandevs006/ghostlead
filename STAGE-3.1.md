# GhostLead — Stage 3.1 | Domain verification

Development milestone `0.3.0-alpha.1`. Keep `main` and the v0.2.0 tag unchanged until the full v0.3 release is ready. This patch implements DNS proof of control, not a monitoring engine.

## Install (Windows / PowerShell)

1. Stop both servers. Check out `develop`, review `git status`, and back up `data/` outside the repository.
2. Copy the patch files to matching paths, replacing only `app/main.py`, `requirements.txt`, and `frontend/src/app/page.tsx`. Add the other files. Do not replace your branded README, database, other tests, globals.css, or package lock.
3. In the repository root:

```powershell
python -m pip install -r requirements.txt
python -m pytest -v
```

4. From `frontend/`:

```powershell
npx tsc --noEmit
npm run build
```

5. Run the backend from the root (`python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload`) and frontend from `frontend/` (`npm run dev`). Sign in at `http://localhost:3000`.

## Verify a registered website

- Select **Verification** in the sidebar and choose a registered website that you control or have explicit permission to monitor.
- Confirm permission, then generate a challenge. A unique TXT record name and value appear. No network lookup happens until you click **Check DNS record**.
- Use the domain's DNS management dashboard to add the exact TXT record. If the DNS provider appends the zone automatically, enter only the relative name; e.g., for `www.example.com` in zone `example.com`, use `_ghostlead-verification.www`. Do not replace existing records.
- Check DNS after propagation. Matching means that the system resolver observed the exact token. A missing record or DNS error never produces a successful verification.
- Challenges expire after 24 hours; successful proof expires after seven days. Generate a fresh challenge and republish it to renew. Revoke proof at any time, and remove the stale TXT record from DNS yourself. Generating a new token invalidates prior proof immediately. Do not upload proof tokens or database files to GitHub.

## Scope and limitations

- DNS proof is per registered site and exact hostname (including `www`), not blanket proof for subdomains, redirects, or paths. Consent is an explicit recorded attestation, not a legal determination of permission. DNS proof is a point-in-time check using the system resolver, not independently validated DNSSEC proof. DNS changes or transfer may not be reflected until the proof expires.
- IP literals, local/reserved suffixes and nonstandard ports are unsupported. Only hostname syntax is checked; this is not a public-IP / SSRF defence. No HTTP requests, form submissions, scans, screenshots, scheduled tasks or real monitoring observations are generated by this stage. Before browser/HTTP discovery, implement destination address validation, DNS rebinding/redirect protection, network isolation, request budgets and explicit scope enforcement.
- A new `domain_proofs` table is created at startup; existing tables and data are not replaced. Deleting a registered website cascades to its proof. Permission and verification timestamps are stored in UTC epoch seconds; UI displays local time. Per-site retries are limited to one per ten seconds for the current challenge. Not a distributed abuse-control mechanism.
- DNS library: dnspython, system resolver, fully qualified TXT name, search suffix disabled, five-second lifetime. See https://dnspython.readthedocs.io/en/stable/resolver-class.html.
- Tests use mocked DNS and isolated SQLite databases. Full Windows and frontend production-build verification must be done locally. No real domain was contacted during package testing.
